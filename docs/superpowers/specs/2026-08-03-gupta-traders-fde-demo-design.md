# Gupta Building Materials — FDE Masterclass Demo: Design Spec

## 1. Context

This is the reference build for the Scaler Academy "Real FDE Simulation" masterclass (see `FDE_Masterclass_Problem_Statement.html` for the full brief). The fictional client, Gupta Building Materials, runs a ₹12 Cr MSME distribution business on Excel, Tally, a handwritten khata, and WhatsApp. The masterclass modernizes this into a unified data + API + dashboard + AI system.

**Session format:** hybrid, with everything pre-built today so nothing is written from scratch live — but each layer is *presented* differently in the 3-hour class:

1. **Narrative framing (no code)** — before touching anything, set up the problem for the learners: what "6 disconnected islands of data" means, how an FDE approaches this kind of mess, and the plan for the next 3 hours.
2. **Data unification — live walkthrough + live run.** The raw-to-Postgres script is pre-built and pre-tested today, but in class it's actually *re-run live* against the raw files (not just shown as a finished result), with a code walkthrough narrating each step as it executes. See §4.4 for the step sequence this walkthrough follows.
3. **Backend + frontend — code walkthrough of the pre-built, already-deployed system.** These are not re-coded or re-run live; the presenter walks through the code and the working dashboard on the deployed Railway URL, explaining the architecture choices.
4. **AI agents — live-coded.** All 4 agents are built and tested in advance as a reference implementation, but in class they're live-coded (narrated/typed from the tested reference), so the "AI" part of the demo happens in front of the audience without risking the plumbing underneath it.

See §11 for the lecture script that ties these four phases together with timing.

## 2. Goals / Non-Goals

**Goals:**
- A single deployed URL, working end-to-end, that survives a live audience demo without surprises.
- All 4 agents tested against the real Claude API today, so tomorrow's live coding has a known-good reference to work from.
- Guaranteed "wow moments" — specific seeded data that reliably reproduces the demo scenarios from the brief (not left to random chance).
- At the end of code generation and project implementation, produce a lecture script covering the entire masterclass, from scoping through implementation to the live URL phase (see §11).

**Non-Goals:**
- Production-grade auth, multi-tenancy, or real customer data — this is a demo build for a single fictional client.
- General-purpose ERP features beyond what the brief's 6 functions require.
- Horizontal scale — data volumes match the brief exactly (~500 SKUs, ~3,000 invoices, ~340 customers, ~200 WhatsApp messages, 12 suppliers).

## 3. Architecture

One Railway project: a single FastAPI service that serves both the REST API and the built React static files (one URL, no CORS), backed by a Railway Postgres add-on. Postgres is used identically in local dev and in production — no SQLite — so there's no "worked locally, broke in prod" risk introduced the night before a live class.

```
Raw messy files (xlsx / csv / json)
        │
        ▼
Ingestion scripts (deterministic parsing + Agent 1 for ambiguous cases)
        │
        ▼
Postgres (products, customers, orders, invoices, credit_ledger,
          suppliers, supplier_rate_cards, whatsapp_messages)
        │
        ▼
FastAPI REST layer  ──►  React dashboard (served by the same FastAPI app)
        │
        ▼
Agents 2 / 3 / 4 invoked from specific endpoints, live during the demo
```

## 4. Data Layer

### 4.1 Raw datasets (generated with intentional messiness)

Generated by one Python script (`generate_data.py`, Faker + seeded randomness) so the "messy before" state matches the brief exactly:

| # | File | Format | Volume | Intentional messiness |
|---|------|--------|--------|------------------------|
| 1 | `stock_register.xlsx` | Excel, 3 sheets | ~500 SKUs | Name variants (3–4 per product), mixed units (bag/bags/BGS), empty/merged cells, some negative qty |
| 2 | `tally_export.csv` | CSV | ~3,000 invoices, 2 yrs | Mixed date formats, ₹ symbols/commas, "CASH" in place of customer, 30% missing GST |
| 3 | `khata_ledger.csv` | CSV | ~340 customers, ~2,100 entries | Hindi-English notes, year-less dates ("14 Jan"), lakh shorthand ("50k liya"), some name-only rows |
| 4 | `whatsapp_orders.json` | JSON | ~200 messages | Hinglish, abbreviations ("sariya", "cem"), item/qty order varies, some voice-note transcriptions |
| 5 | `supplier_rates.csv` | CSV | 12 suppliers, ~150 products | Stale prices (some 6mo old), mixed units per supplier, free-text discount tiers, some "call for rate" |

### 4.2 Seeded "golden path" records

The following are deliberately seeded (not left to random generation) so the live demo reliably reproduces the brief's exact showcase moments:

- **Vinod Builders** — ₹4.1L overdue, 82 days outstanding, so entering a new ₹3.5L+ order for this customer always triggers Agent 3's high-risk flag.
- **Cement seasonality** — a monsoon demand spike baked into the 2-year sales history for Ambuja/UltraTech cement, so Agent 4's reorder forecast reliably appears.
- **One fixed WhatsApp message** (matching the brief's "10mm sariya 2 ton, pipe 1 inch 50 piece" example) reserved as the exact text to paste live for the Agent 2 demo.

### 4.3 Unified schema (Postgres, SQLAlchemy models)

- `products` — id, name, brand, category, unit, hsn_code, current_stock
- `customers` — id, name, phone, area
- `orders` / `order_items` — order header + line items, source (whatsapp/call/walk-in), delivery address/time
- `invoices` — from Tally export: date, amount, gst_number (nullable), payment_status
- `credit_ledger` — customer_id, date, type (debit/credit), amount, note, source_raw (original khata text)
- `suppliers` / `supplier_rate_cards` — supplier_id, product_id, price, unit, date, discount_tier_text
- `whatsapp_messages` — id, raw_text, customer_id (nullable FK, filled in after parsing), received_at, parsed_order_id (nullable FK), raw_metadata (JSONB for variable/unstructured fields)

**Decision: Postgres only, no separate NoSQL store.** At ~200 WhatsApp records, there's no scale or schema-flexibility need that a JSONB column doesn't already cover. A second data store (e.g. MongoDB) would double the infrastructure surface (a second provisioned service, a second credential, a second failure mode) for no benefit at this size — a bad trade for a live demo where fewer moving parts is a feature.

### 4.4 Raw-to-Postgres steps (the live walkthrough sequence)

This is the step sequence the data-unification script follows — it's written to be run and narrated step by step in class, not just executed as one opaque batch job:

1. **Extract** — read each raw file (`stock_register.xlsx`, `tally_export.csv`, `khata_ledger.csv`, `whatsapp_orders.json`, `supplier_rates.csv`) into a pandas DataFrame per source, unchanged.
2. **Deterministic cleanup** — fix what a script can fix without judgment calls: parse mixed date formats, strip ₹/commas from amounts, standardize obvious unit spellings, drop fully-empty rows.
3. **Ambiguous-case resolution (Agent 1)** — hand the still-ambiguous product name variants to the cleaning agent to dedupe and map to the catalog; this is the "AI handled what no regex could" moment, shown as a before/after diff.
4. **Load** — insert into the unified Postgres schema (§4.3), one source at a time, in dependency order (products → customers/suppliers → orders/invoices/credit_ledger/rate_cards/whatsapp_messages).
5. **Verify** — run row-count and spot-check queries against Postgres to confirm the load matches expectations, live, so the audience sees the unified data land correctly.

## 5. Backend — FastAPI

- `GET/POST /products`, `/customers`, `/suppliers`, `/rate-cards`
- `GET/POST /orders` — creating an order synchronously runs the Agent 3 credit-risk check and returns the flag inline
- `GET /credit/{customer_id}` — ledger + aging buckets
- `GET /credit/{customer_id}/risk` — Agent 3, standalone (usable outside order creation)
- `POST /agents/parse-order` — Agent 2 (WhatsApp text → structured order)
- `GET /agents/demand-forecast` — Agent 4

Agent 1 (cleaning) runs as a one-time ingestion step, not a live endpoint — it produces the clean catalog before the demo starts, and its before/after is shown as a diff in the Hour-1 walkthrough, not triggered live.

`ANTHROPIC_API_KEY` is a backend-only secret (Railway env var, never sent to the frontend, never committed to git) used by the Anthropic Python SDK to call Claude for all 4 agents.

## 6. Frontend — React Dashboard

Four mobile-responsive views:
- **Overview** — stock summary, today's orders, credit-outstanding aging chart, low-stock alerts
- **Orders** — order list + a "paste WhatsApp message" box wired live to Agent 2
- **Customers/Credit** — table with aging buckets and Agent 3 risk badges
- **Suppliers** — rate card comparison

## 7. AI Agent Layer

All 4 agents are built and tested against the real Claude API today, as a safety net for tomorrow's live coding:

1. **Data Cleaning & Normalization** — dedupes SKU name variants, standardizes units/categories, maps to the clean catalog.
2. **WhatsApp Order Parser** — Hinglish text → structured order (customer match, items with qty/unit, delivery address/time).
3. **Smart Credit Risk Analyzer** — given a customer + new order amount, computes aging from the ledger, returns a risk flag + recommendation.
4. **Demand Intelligence & Reorder** — given a product's sales history, detects seasonality, forecasts 30-day demand, suggests a reorder quantity.

Each is a self-contained Python module with a clear function signature, a structured-output prompt (JSON schema via the Anthropic SDK's tool use), and few-shot examples drawn from the actual generated data. Tomorrow, the live session narrates/types from this tested reference rather than improvising cold.

## 8. Deployment

One Railway project: the FastAPI service (serving API + built React static files) + a Railway Postgres add-on. `ANTHROPIC_API_KEY` and `DATABASE_URL` set as Railway environment variables. Deployed and smoke-tested today, so tomorrow is "open the URL."

## 9. Verification Plan

Before this is considered done today:
- Data-generation script produces correct row counts and the specified messiness for all 5 datasets.
- All backend endpoints tested locally against Postgres (not SQLite).
- All 4 agents tested against real Claude API responses (not mocked).
- One full rehearsal through the exact golden-path scenarios (Vinod Builders order, the fixed WhatsApp message, the monsoon forecast) run against the deployed Railway URL, not just locally.

## 11. Lecture Script Deliverable

A standalone presenter script, written last (after everything above is built, deployed, and rehearsed), covering the full 3-hour class end to end. This is what the presenter actually reads from/rehearses with — not just a recap of the spec.

**Contents:**
